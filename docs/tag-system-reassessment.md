# Tag system 整合重新評估

2026-09-11。依據 [PR #62](https://github.com/hydai/prism.oshi.tw/pull/62)、原分支七個 commit、目前程式與靜態資料，以及最新 `master`（`c0b0919`）分析。使用者已確認沒有另外的原始 issue。本文是建議，尚未實作新的產品設計，也未查詢或變更 production D1。

## 建議

保留「作品共用資訊／具體演出資訊」兩個作用範圍、受控 tag ID，以及 D1 → 靜態匯出的架構。把自動分類從一次性資料 migration 改成可接受、拒絕與重新評估的建議；把演出標註放進歌回與時間戳編輯流程。先讓一小批確認過的資料能正確搜尋與播放，再擴充分類覆蓋率。

目前 PR 同時承擔三個產品：觀眾探索、管理者編目、自動分類。主要問題是這三者的上線與維護被綁在一起，分類結果又直接成為正式資料。

## 原本要解決什麼

PR 說明可還原出三個目標：

1. 觀眾能依語言、曲風、氛圍、演唱形式、作品來源找歌，桌面和手機都可用，並能搜尋標籤名稱。
2. 管理者對共用作品只需標註一次，可批次處理，也能標註個別演出。
3. 功能推出時要有足夠資料，避免先手動分類幾千首歌才有使用價值。

第 3 點是初始 catalog 的動機；「用 artist metadata 推斷後直接 seed 全庫」是目前選用的手段，並不是前兩個目標的必要條件。沒有原始 issue 可提供更細的驗收條件，因此以下優先順序是建議，而非已確認需求。

## 目前實作

| 部分 | 行為與程式位置 |
|---|---|
| 字典 | [`lib/tags.ts`](../lib/tags.ts) 定義五類、穩定 ID、中文名稱、別名、可寫入 scope。新增種類需要更新程式。 |
| 儲存 | `works.tags` 放 genre／mood／source；`performances.tags` 放 language／style；`songs.tags` 只作舊資料相容讀取。 |
| 編輯 | [`GlobalWorks.tsx`](../admin/ui/src/pages/GlobalWorks.tsx) 提供單筆與批次作品標註；[`SongDetail.tsx`](../admin/ui/src/pages/SongDetail.tsx) 逐次編輯演出；API 限制 scope 與 curator 權限。 |
| 自動分類 | [`classify.ts`](../tools/tag-catalog/classify.ts) 使用標題、文字系統、原唱對照表、跨歌曲訊號、Apple artist snapshot、Vocaloid producer 等線索。 |
| 種子資料 | [`data/tag-catalog.json`](../data/tag-catalog.json) 保留逐筆 evidence；migration 0011 將種子與既有資料做聯集。正常 sync 不重新套 seed。 |
| 匯出 | [`sync-data/sync.ts`](../tools/sync-data/sync.ts) 匯出繼承層與個別演出標籤；loader 還原有效標籤及卡片用聯集。 |
| 搜尋與播放 | [`archive.ts`](../app/lib/archive.ts) 同類 OR、跨類 AND，與年份／歌回等條件共同作用於同一次演出。Grouped 結果只留下命中的版本，播放也跟隨這個集合。 |

資料流：

```text
works.tags + 舊 songs.tags → inheritedTags
inheritedTags + performance.tags → 這次演出的有效標籤
所有演出有效標籤的聯集 → 歌曲卡片摘要
```

聯集可以顯示「這首歌有哪些版本」，不能證明某個版本同時符合所有條件。例如 2024 年日文獨唱、2025 年中文合唱，搜尋「2024 年＋中文＋合唱」應該沒有結果。分支後續修正已處理這點，應保留相關測試。

本機資料盤點：

| 項目 | 數量 |
|---|---:|
| 最新靜態歌曲／演出 | 5,409／9,070 |
| 靜態資料中有非空標籤的歌曲／演出 | 0／0 |
| 8 月初 seed 的歌曲／演出母體 | 4,993／8,541 |
| seed 有作品標籤的 work | 1,417 |
| seed 有演出標籤的 performance | 6,247 |
| seed 母體中可獲得有效標籤的歌曲 | 3,621，約 72.5% |

6,247 個 seed performance ID 都仍存在於目前靜態資料，但母體已成長。這只表示 ID 尚可對應，不代表分類已核實。PR body 所寫「committed static JSON already contains effective tags」也已不符合分支末版；末版文件與程式改成先寫入 D1，再 sync 才出現標籤。

## 需要重新決定的地方

**推估與確認沒有分開。** 分類器把原唱／歌名推得的語言寫到每次演出，儲存位置雖然正確，證據未必描述該次演出。原唱以日語為主，不能證明某段翻唱沒有改詞。Apple artist catalog 的主流曲風也不等於每一首作品的曲風。Evidence 留在 repository seed 中，正式資料本身只有 ID 陣列，沒有可操作的接受／拒絕紀錄。

**分類定義仍有混用。** `style:acoustic` 同時對應「自彈自唱」和「不插電」，兩者不等價；`language:other` 的別名包含「多語」，但多語可以直接有多個 language ID。「原創曲」被存在全域 work：若意思是「這位 VTuber 的原創」，就需要 work 與創作者的關係，否則其他人的翻唱也會繼承。「氛圍」尤其可能隨編曲改變，目前卻固定為 work scope。這些定義應先決定，避免日後繼續做 scope repair。

**管理入口與資料負擔不一致。** Bulk editor 和「Untagged only」在作品層，最多只能推進作品標籤；數量更多的語言／演唱形式在演出層，仍要進 Song Detail 逐筆編輯。「有任一 tag」也不代表重要欄位已補齊。實際工作隊列應是「缺演唱語言」「有待審核建議」「缺作品來源」，並連到可播放驗證的演出。

**一次性 seed 缺少更正生命週期。** Migration 聯集避免覆寫人工資料，但重新套用會恢復人工刪除的標籤，所以目前只能禁止交接後重跑。分類器修好後，如何撤回舊推估、保留人工否決、處理合併後的 ID，仍沒有完整工作流程。應讓 schema migration 只負責儲存結構，分類資料另走可預覽的匯入／審核流程。

**編輯需要跟既有交易與版本管理接合。** 批次 work delta 已在 SQL 內合併，是值得保留的設計。單筆全量覆寫沒有預覽版本檢查；取代歌回的流程會先讀取標籤，再刪除／重建演出，這段讀寫之間仍可能與另一位管理者衝突。重新設計時應沿用 master 的 revision／stale-preview 概念，並保留 performance ID 的既有身分語意；這次 rebase 沒有擴大為替換匯入流程的重寫。

**未來資料分片需要保留條件關聯。** [Issue #60](https://github.com/hydai/prism.oshi.tw/issues/60) 的 catalog＋年度 performance 分片已有設計。只把 `song.tags` 聯集放到 catalog，無法支援「年份＋語言＋形式」的精確判斷，catalog 的預設 latest 也可能不是命中的演出。實作分片時需共同設計可查詢的演出索引，或在精確篩選／播放前載入必要分片，不能以作品聯集當成完整結果。

## 可選方向

| 方向 | 好處 | 代價／限制 |
|---|---|---|
| 照目前 PR 整包推出 | 分類覆蓋率很快提高，UI 已完整 | 一次承接五類定義、seed 更正與人工維護問題。 |
| 全部只標在作品上 | 編輯數量少，結構簡單 | 不能正確表達翻唱語言、合唱、清唱等版本差異。 |
| **確認資料核心＋建議審核，分階段推出** | 保留現有大部分正確邏輯，能逐步累積可信資料 | 初期覆蓋率較低，需做好批次審核效率。 |
| 通用可自訂標籤平台 | 分類、權限與資料模型最有彈性 | 增加管理介面、字典治理與關聯表維護，尚無需求證明值得。 |

建議第三個方向。現階段仍可用受控 ID 與 JSON 陣列儲存正式標籤；不必為了這次整合立刻建立通用 taxonomy engine。

## 建議的最小落地順序

1. **先定義少數明確欄位。** 演唱語言為 performance 多選；演唱形式只收明確可核實的定義；動畫／遊戲／Vocaloid 等來源以作品為單位。氛圍暫緩，曲風先限人工確認。若需要「原曲語言」，使用獨立欄位，不能取代「這次演唱的語言」。
2. **接上既有編輯流程。** 在 Stream Detail／Stamp Editor 選取演出、播放確認、批次套標籤；Song Detail 作例外修正。Work picker 顯示目前共用標籤與修改影響範圍，避免管理者在兩個頁面來回猜資料來源。
3. **將 classifier 降為建議來源。** 建議至少記錄 scope、entity ID、tag ID、evidence、source／rule version、待審／接受／拒絕狀態及 reviewer。相同版本重跑不重建已拒絕建議；實體失效或合併需重新對應／複核，不能盲目重放。接受動作更新正式 tags，並在同一交易保存審核結果和必要的版本防護。
4. **先審一批常聽歌曲與最近歌回。** 同樣的證據可批次審核，但以清楚的歌曲／演出清單確認；不要把全庫百分比當成正確率。工作隊列依「待審建議、缺語言、播放需求」排序。
5. **前台只使用正式資料。** 沿用現有 OR／AND 與逐演出匹配，讓卡片顯示命中的標籤／版本；播放與加入佇列都使用相同結果集合。未標註代表未知，不能自動落到「其他語言」。保留既有靜態匯出，不新增 runtime API 依賴。
6. **驗證後再擴大。** 觀察找歌是否更快、零結果是否易理解、管理者確認／撤回是否順手，再決定更多分類、URL 篩選狀態與資料分片。先釐清 chip 數字是「包含此 tag 的筆數」還是「加入條件後的總數」，並區分作品數與演出數。

驗收應包含：同一作品兩種語言互不污染、年份和標籤命中同一次演出、所有播放入口與篩選一致、拒絕建議重跑不復活、人工修改 sync 後不被覆寫、同秒共用標籤變更讓所有相關 streamer 過期，以及合併／重匯入時的標籤與播放身分保留。

## 本次 rebase 的處理範圍

保留原分支的功能設計，將前台狀態接到 master 的 Archive providers、Admin 接回 `useApiResource` 與共用表格元件、標籤寫入接到新的 catalog SQL pipeline、匯出接到單次 snapshot 查詢與原有播放排序。Migration 改號為 0010／0011，並補上共用 work tag 的匯出 revision trigger。新的建議審核與編輯器整合仍只是本文提案。
